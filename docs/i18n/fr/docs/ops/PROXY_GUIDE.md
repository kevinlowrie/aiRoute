## Pourquoi utiliser des proxys ?

De nombreux fournisseurs AI restreignent l'accès par région géographique. Développeurs en** Russie, Chine, Iran, Cuba, Turquie** , et d'autres pays rencontrent des erreurs telles que :

```
unsupported_country_region_territory
```

Même en dehors des régions bloquées, les proxys sont utiles pour :

| Cas d'utilisation              | Description                                                                      |
| ------------------------------ | -------------------------------------------------------------------------------- |
| **Contournement géographique** | Accédez OpenAI, Anthropic, Codex, Copilot depuis les pays bloqués                |
| **rotation IP**                | Répartissez les requêtes sur plusieurs IPs pour éviter toute limitation de débit |
| **Confidentialité**            | Cachez votre vrai IP aux fournisseurs en amont                                   |
| **Conformité**                 | Acheminer le trafic vers des juridictions spécifiques                            |
| **Essai**                      | Simuler les demandes de différentes régions                                      |

## État du proxy par défaut pour les nouveaux comptes

Dans** Paramètres → Proxy → Configuration globale** , utiliser** Activer le proxy par défaut pour les nouvelles connexions** pour choisir l'état proxy initial des comptes de fournisseur nouvellement ajoutés.

Le nouveau paramètre contrôle l'état du proxy initial des comptes de fournisseur nouvellement ajoutés. Il ne modifie pas les comptes existants et ne remplace pas le commutateur de proxy global. Sa valeur initiale conserve le comportement précédent. Désactivez-le une fois pour créer de futurs comptes avec le proxy désactivé par défaut.

La préférence est stockée sous `defaultNewConnectionProxyEnabled` via les paramètres API existants. La valeur par défaut est `true` lorsqu'elle n'est jamais enregistrée. L'enregistrement `false` prend effet pour les nouveaux comptes suivants sans redémarrage. `POST /api/providers` accepte un `proxyEnabled` booléen strict facultatif ; un `true` ou `false` explicite a priorité sur la valeur par défaut de création. L'omission sur un compte en double ou la reconnexion OAuth préserve l'état stocké de ce compte. Les comptes individuels peuvent toujours être activés ou désactivés par la suite.

Les transferts de fournisseur sélectifs utilisent la valeur par défaut de l'installation de destination pour les nouveaux comptes et préservent la politique de destination lors du remplacement des comptes existants. Les bascules de proxy ne sont pas des champs de transfert portables. La restauration par sauvegarde complète et la migration historique JSON/SQL conservent leur sémantique de restauration existante, y compris les valeurs de compte enregistrées et les valeurs par défaut des schémas hérités ; une restauration complète des paramètres peut également restaurer cette préférence.

Cette préférence n’attribue pas de proxy et n’établit pas qu’il est sain ou en cours d’utilisation. Le routage réel dépend toujours du commutateur proxy global et de la configuration proxy applicable. Les fournisseurs synthétiques sans compte persistant, le trafic OAuth avant la création du compte, les proxys environment/system et la mise en réseau des backends externes sortent de son champ d'application.

## Système proxy à 4 niveaux

OmniRoute prend en charge la configuration du proxy sur** quatre périmètres indépendants** , résolu par ordre de priorité :

```
Priority Resolution Order (highest → lowest):

  1. 🔵 Account/Connection Proxy  →  per API key / OAuth connection
  2. 🟡 Provider Proxy            →  per provider (e.g., all OpenAI traffic)
  3. 🟠 Combo Proxy               →  per combo/routing configuration
  4. 🟢 Global Proxy              →  all traffic, all providers
```

### Comment fonctionne la résolution

Lorsque OmniRoute envoie une requête à un fournisseur en amont, il appelle `resolveProxyForConnectionFromRegistry()` qui vérifie chaque niveau dans l'ordre :

1. **Au niveau du compte** — Existe-t-il un proxy attribué à cette connexion spécifique ID?
2. **Au niveau du fournisseur** — Existe-t-il un proxy attribué à ce fournisseur (par exemple, `openai`) ?
3. **Au niveau mondial** — Existe-t-il un proxy global configuré ?
4. **Pas de procuration** — Connexion directe au fournisseur.

Le premier match gagne. Cela signifie que vous pouvez définir un proxy global comme solution de secours, mais le remplacer pour des fournisseurs ou des connexions spécifiques.

### Ce qui est proxy

| Type de trafic            | Par procuration ? | Remarques                                          |
| ------------------------- | ----------------- | -------------------------------------------------- |
| Fins de discussion        | ✅                | Toutes les demandes `/v1/chat/completions`         |
| Intégrations              | ✅                | `/v1/embeddings`                                   |
| Génération d'images       | ✅                | `/v1/images/generations`                           |
| Audio (TTS/STT)           | ✅                | `/v1/audio/*`                                      |
| échange de jetons OAuth   | ✅                | Résout `unsupported_country_region_territory`      |
| Tests de connexion        | ✅                | Le bouton « Tester la connexion » utilise un proxy |
| Actualisation du jeton    | ✅                | Renouvellement OAuth en arrière-plan               |
| Synchronisation du modèle | ✅                | Listage et découverte de modèles                   |

## Registre proxy (CRUD)

Le registre proxy est une table SQLite (`proxy_registry`) qui stocke tous vos proxys. Chaque mandataire dispose de :

| Champ      | Taper  | Description                                             |
| ---------- | ------ | ------------------------------------------------------- |
| `id`       | UUID   | Identifiant unique                                      |
| `name`     | Chaîne | Étiquette lisible par l'homme                           |
| `type`     | Chaîne | Protocole : `http`, `https`, `socks5`                   |
| `host`     | Chaîne | Nom d'hôte du proxy ou IP                               |
| `port`     | Entier | Numéro de port                                          |
| `username` | Chaîne | Nom d'utilisateur d'authentification (chiffré au repos) |
| `password` | Chaîne | Mot de passe d'authentification (chiffré au repos)      |
| `region`   | Chaîne | Étiquette de région géographique                        |
| `notes`    | Chaîne | Notes en texte libre                                    |
| `status`   | Chaîne | `active` ou `inactive`                                  |
| `source`   | Chaîne | `manual` ou `oneproxy`                                  |

### Créer un proxy

**Via le tableau de bord :**

1. Aller à** Paramètres du proxy →**
2. Cliquez** Ajouter un proxy**
3. Remplissez le type, l'hôte, le port et les informations d'authentification facultatives
4. Sauvegarder

**Via API:**

```bash
curl -X POST http://localhost:20128/api/v1/management/proxies \
  -H "Content-Type: application/json" \
  -d '{
    "name": "US Proxy",
    "type": "http",
    "host": "proxy.example.com",
    "port": 8080,
    "username": "user",
    "password": "pass",
    "region": "US"
  }'
```

### Mettre à jour un proxy

```bash
curl -X PATCH http://localhost:20128/api/v1/management/proxies \
  -H "Content-Type: application/json" \
  -d '{
    "id": "proxy-uuid-here",
    "host": "new-proxy.example.com",
    "port": 9090
  }'
```

> **Note:** Les informations d'identification sont conservées sauf si vous envoyez explicitement des remplacements non vides. L'envoi de chaînes vides pour `username`/`password` conservera les valeurs stockées.

### Supprimer un proxy

```bash
# Fails if proxy is assigned to any scope
curl -X DELETE "http://localhost:20128/api/v1/management/proxies?id=proxy-uuid"

# Force delete (removes assignments too)
curl -X DELETE "http://localhost:20128/api/v1/management/proxies?id=proxy-uuid&force=1"
```

### Liste des proxys

```bash
curl "http://localhost:20128/api/v1/management/proxies?limit=50&offset=0"
```

### Affectation de proxys aux étendues

```bash
# Assign to global scope
curl -X PUT http://localhost:20128/api/settings/proxy \
  -H "Content-Type: application/json" \
  -d '{"level": "global", "proxy": {"type":"http","host":"proxy.example.com","port":8080}}'

# Assign to a specific provider
curl -X PUT http://localhost:20128/api/settings/proxy \
  -H "Content-Type: application/json" \
  -d '{"level": "provider", "id": "openai", "proxy": {"type":"socks5","host":"socks.example.com","port":1080}}'

# Assign to a specific connection/key
curl -X PUT http://localhost:20128/api/settings/proxy \
  -H "Content-Type: application/json" \
  -d '{"level": "key", "id": "connection-uuid", "proxy": {"type":"http","host":"key-proxy.com","port":3128}}'
```

### Résolution d'un proxy efficace

Vérifiez quel proxy serait utilisé pour une connexion donnée :

```bash
curl "http://localhost:20128/api/settings/proxy?resolve=connection-uuid"
```

Renvoie le proxy résolu avec son niveau (`account`, `provider` ou `global`) et sa source.

### Attribution groupée

Attribuez un proxy à plusieurs fournisseurs ou connexions à la fois :

```bash
curl -X POST http://localhost:20128/api/v1/management/proxies/bulk-assign \
  -H "Content-Type: application/json" \
  -d '{
    "scope": "provider",
    "scopeIds": ["openai", "anthropic", "codex"],
    "proxyId": "proxy-uuid"
  }'
```

### Import/Export

Les procurations sont incluses dans le**Backup/Restore** système. Lorsque vous exportez votre configuration OmniRoute :

1. Aller à** Tableau de bord Paramètres → Sauvegarde →**
2. Cliquez** Exporter** Le registre proxy — et les affectations sont inclus
3. Pour restaurer, cliquez sur** Importer** et téléchargez le fichier de sauvegarde

Le registre proxy prend également en charge** upsert par le port + de l'hôte** — si vous importez un proxy qui existe déjà (même hôte et même port), il se met à jour au lieu de créer un doublon.

### Migration héritée

Si vous avez configuré des proxys dans une ancienne version (pré-registre), OmniRoute les migre automatiquement :

```
Legacy key_value store → proxy_registry + proxy_assignments
```

Cela se produit une fois au premier démarrage après la mise à niveau. Utilisez `migrateLegacyProxyConfigToRegistry({ force: true })` pour réexécuter.

## Marché de proxy gratuit 1proxy

> 🆕** Contribué par [@oyi77](https://github.com/oyi77)** — PR [#1847](https://github.com/diegosouzapw/OmniRoute/pull/1847) (problème [#1788](https://github.com/diegosouzapw/OmniRoute/issues/1788) )

OmniRoute s'intègre avec le** [1 proxy](https://1proxy-api.aitradepulse.com)** plateforme communautaire pour donner accès à** des centaines de proxys gratuits et validés** du monde entier. C'est parfait pour les utilisateurs qui ne disposent pas de leur propre infrastructure proxy.

### Comment ça marche

```
┌─────────────┐     Sync      ┌─────────────────┐    Rotate     ┌──────────┐
│  1proxy API │ ────────────▶ │  proxy_registry  │ ────────────▶ │ Provider │
│  (external) │   up to 500   │  source=oneproxy │  by quality   │   API    │
└─────────────┘    proxies    └─────────────────┘               └──────────┘
```

1. **Synchroniser** — OmniRoute récupère les proxys validés du 1proxy API
2. **Magasin** Les proxys — sont enregistrés dans la même table `proxy_registry` avec `source = 'oneproxy'`
3. **Filtre** — Filtrer par protocole, pays, niveau de qualité
4. **Tourner** — Choisissez le meilleur proxy en utilisant des stratégies de qualité, aléatoires ou séquentielles
5. **Dégradation automatique** — Les proxys défaillants voient leur score de qualité réduit ; en dessous du seuil → marqué inactif

### Synchronisation des proxys

**Via le tableau de bord :**

1. Aller à** Paramètres → 1proxy** languette
2. Cliquez** "Synchroniser maintenant"**
3. Afficher les statistiques : nombre total de proxys, nombre d'actifs, qualité moyenne, répartition par pays

**Via API:**

```bash
# Trigger sync
curl -X POST http://localhost:20128/api/settings/oneproxy \
  -H "Content-Type: application/json" \
  -d '{}'

# Response:
# { "success": true, "added": 127, "updated": 45, "failed": 2, "total": 172 }
```

### Filtrage des proxys

```bash
# Filter by protocol
curl "http://localhost:20128/api/settings/oneproxy?protocol=socks5"

# Filter by country
curl "http://localhost:20128/api/settings/oneproxy?countryCode=US"

# Filter by minimum quality score
curl "http://localhost:20128/api/settings/oneproxy?minQuality=80"

# Combine filters
curl "http://localhost:20128/api/settings/oneproxy?protocol=http&countryCode=DE&minQuality=70"
```

### Niveaux de qualité du proxy

Chaque proxy 1proxy est livré avec des métadonnées :

| Champ           | Description                                          |
| --------------- | ---------------------------------------------------- |
| `qualityScore`  | Note de 0 à 100 à partir de la validation de 1 proxy |
| `latencyMs`     | Latence réseau mesurée                               |
| `anonymity`     | `transparent`, `anonymous` ou `elite`                |
| `googleAccess`  | Si le proxy peut accéder aux services Google         |
| `countryCode`   | Code pays ISO à deux lettres                         |
| `lastValidated` | Horodatage de la dernière validation                 |

Les scores de qualité sont ajustés dynamiquement :

- **Demandes ayant échoué** réduire le score de 10 points
- **Le score tombe à ≤ 10** Le proxy → est marqué `inactive`
- Les proxys inactifs sont exclus de la rotation

### Stratégies de rotation

```bash
# Rotate by quality (best proxy first) — default
curl -X POST http://localhost:20128/api/settings/oneproxy/rotate \
  -H "Content-Type: application/json" \
  -d '{"strategy": "quality"}'

# Random rotation
curl -X POST http://localhost:20128/api/settings/oneproxy/rotate \
  -d '{"strategy": "random"}'

# Sequential (least recently validated first)
curl -X POST http://localhost:20128/api/settings/oneproxy/rotate \
  -d '{"strategy": "sequential"}'
```

### Disjoncteur

Le 1proxy sync dispose d'un disjoncteur intégré :

- Après** 5 échecs de synchronisation consécutifs** , les tentatives de synchronisation ultérieures sont bloquées
- Réinitialiser avec : `resetOneproxyCircuitBreaker()` ou redémarrer le serveur
- Le statut de synchronisation est disponible sur `GET /api/settings/oneproxy?action=status`

### Effacement des proxys 1proxy

```bash
# Delete a single 1proxy proxy
curl -X DELETE "http://localhost:20128/api/settings/oneproxy?id=proxy-uuid"

# Clear ALL 1proxy proxies (manual proxies are untouched)
curl -X DELETE "http://localhost:20128/api/settings/oneproxy?clearAll=1"
```

## Anti-détection et furtivité

OmniRoute ne se contente pas d'acheminer le trafic via un proxy — il donne au trafic une apparence légitime :

### Usurpation d'empreintes digitales TLS

Utilise `wreq-js` pour générer des empreintes digitales TLS de type navigateur, en contournant les systèmes de détection de robots qui signalent les poignées de main TLS non liées au navigateur.

### Correspondance d'empreintes digitales CLI

Le** Bascule d'empreinte digitale CLI** (`Settings → Security`) réorganise les en-têtes HTTP et les champs de corps JSON pour qu'ils correspondent à la signature exacte des binaires CLI natifs (Claude Code, Codex, etc.). Cela fonctionne** au sommet de** le mandataire :

```
Your IP (blocked) → Proxy IP (US) → Provider API
                    + TLS spoof
                    + CLI fingerprint
```

Vous obtenez les deux** masquage IP** et** demander l'authenticité** simultanément.

### Proxy IP Préservation

Des badges à code couleur dans le tableau de bord indiquent quel niveau de proxy est actif :

| Badge | Niveau      | Signification                              |
| ----- | ----------- | ------------------------------------------ |
| 🟢    | Mondial     | Tout le trafic passe par ce proxy          |
| 🟡    | Fournisseur | Seul le trafic de ce fournisseur est proxy |
| 🔵    | Connexion   | Ce key/account spécifique utilise ce proxy |

Le badge affiche également le proxy IP résolu pour vérification.

## Modes proxy en amont

Pour les fournisseurs qui utilisent le modèle CLIProxyAPI, OmniRoute prend en charge trois modes proxy en amont :

| Mode          | Description                                              |
| ------------- | -------------------------------------------------------- |

## Dépannage

### " Le proxy SOCKS5 est désactivé "

Définissez `ENABLE_SOCKS5_PROXY=true` dans votre fichier `.env` et redémarrez.

### Erreurs "socket raccrocher" via proxy

Ceci est normal avec les proxys bon marché qui abandonnent les connexions inactives. OmniRoute gère déjà cela en :

- Désactivation du maintien en vie sur les connexions proxy (`keepAliveTimeout: 1`)
- Désactivation du pipeline (`pipelining: 0`)
- Mise en cache des répartiteurs pour éviter les poignées de main répétées

Si le problème persiste, essayez un autre proxy ou utilisez la fonction de rotation 1proxy.

### "unsupported_country_region_territory" pendant OAuth

Assurez-vous que le proxy est configuré** avant** démarrer le flux OAuth. OmniRoute achemine l'échange de jetons OAuth via le proxy configuré. Définissez d’abord un proxy global ou au niveau du fournisseur, puis connectez-vous.

### Le proxy n'est pas utilisé

Vérifiez l'ordre de résolution :

1. Vérifier avec `GET /api/settings/proxy?resolve=your-connection-id`
2. Vérifiez si le proxy `status` est `active` (pas `inactive`)
3. Assurez-vous que la portée de l'attribution du proxy correspond à votre connexion

### Échec de la synchronisation 1proxy

Vérifiez l'état de la synchronisation :

```bash
curl "http://localhost:20128/api/settings/oneproxy?action=status"
```

Si `consecutiveFailures >= 5`, le disjoncteur s'est déclenché. Redémarrez le serveur pour réinitialiser ou attendez la réinitialisation manuelle.

## Vérification de l'état du proxy (v3.8.16 +)

OmniRoute** proxy à échec rapide** Le mécanisme (`src/lib/proxyHealth.ts`) détecte les proxys morts dans < 2s via une vérification rapide de la connexion TCP, puis** met en cache le résultat** pour éviter les frais généraux par requête.

### Comment ça marche

```
Request ──▶ ProxyHealthCache.get(url)
             │
             ├─ Cache hit + fresh?  ──▶ return cached status
             │
             └─ Cache miss / stale?  ──▶ TCP connect to host:port
                                          (timeout: FAST_FAIL_TIMEOUT_MS)
                                          ──▶ cache for HEALTH_CACHE_TTL_MS
                                          ──▶ return result
```

Sans cela, un proxy mort bloquerait chaque demande de `PROXY_TIMEOUT_MS` complet (30 s par défaut) avant d'échouer.

### Variables d'environnement réglables

| Variable                     | Défaut  | But                                                          |
| ---------------------------- | ------- | ------------------------------------------------------------ |
| `PROXY_FAST_FAIL_TIMEOUT_MS` | `2000`  | délai d'expiration de la connexion TCP par contrôle de santé |
| `PROXY_HEALTH_CACHE_TTL_MS`  | `30000` | Combien de temps un résultat de santé est mis en cache       |

**Valeurs recommandées :**

| Scénario                    | Délai d'expiration rapide | Cachez TTL | Raisonnement                                                                                   |
| --------------------------- | ------------------------- | ---------- | ---------------------------------------------------------------------------------------------- |
| Passerelle API à haut débit | 1500 ms                   | 60 000 ms  | Un cache agressif, rapide et plus long pour réduire les contrôles                              |
| Nœuds géo-distribués        | 3000 ms                   | 15 000 ms  | Les réseaux plus lents nécessitent plus de temps ; cache plus court pour un basculement rapide |
| Développement/test          | 1000 ms                   | 10 000 ms  | Itération rapide sur les proxys locaux                                                         |
| Furtif / anti-détection     | 2500 ms                   | 45 000 ms  | Évitez les sondages rapides qui pourraient déclencher des limites de débit                     |

### Inspection de l'état du proxy

```ts
import { getAllProxyHealthStatuses, invalidateProxyHealth } from "omniroute/proxyHealth";

const statuses = getAllProxyHealthStatuses();
for (const s of statuses) {
  console.log(`${s.proxyUrl} → healthy=${s.healthy}, stale=${s.stale}`);
}

// Force re-check a specific proxy
invalidateProxyHealth("http://user:pass@203.0.113.7:8080");
```

L'indicateur `stale` est `true` lorsque l'entrée du cache a dépassé `HEALTH_CACHE_TTL_MS` et la requête suivante déclenchera une nouvelle vérification.

### Valeurs par défaut du type de proxy

Le bilan de santé utilise des valeurs par défaut raisonnables basées sur le schéma URL :

| Schème                     | Port par défaut |
| -------------------------- | --------------- |
| `http://`                  | 8080            |
| `https://`                 | 443             |
| `socks5://` / `socks5h://` | 1080            |

Les ports personnalisés dans URL (`http://host:9999`) ont toujours priorité sur le schéma par défaut.

## Analyse proxy et observabilité

OmniRoute suit l'utilisation par proxy pour aider les opérateurs à diagnostiquer les modèles de routage, les pics de latence et les pannes récurrentes.

### Ce qui est suivi

Pour chaque requête via un proxy configuré, OmniRoute enregistre :

| Métrique     | Description                                                       |
| ------------ | ----------------------------------------------------------------- |
| `proxy_url`  | Proxy complet URL (avec informations d'authentification masquées) |
| `provider`   | Fournisseur amont ID (openai, anthropic, etc.)                    |
| `latency_ms` | Durée totale aller-retour, y compris la prise de contact du proxy |
| `connect_ms` | temps de connexion TCP uniquement                                 |
| `status`     | code d'état HTTP depuis l'amont                                   |
| `error`      | Classe d'erreur si la demande a échoué                            |
| `timestamp`  | ISO 8601 UTC                                                      |

### Accéder aux données

```bash
# Recent proxy events
curl -H "Authorization: Bearer $OMNIROUTE_KEY" \
  "http://localhost:20128/api/usage/proxy-logs?limit=100"
```

Le véritable point final est `/api/usage/proxy-logs` (voir `src/app/api/usage/proxy-logs/route.ts`). Ce point de terminaison prend en charge :

- `GET /api/usage/proxy-logs` — récupère les journaux du proxy
- `DELETE /api/usage/proxy-logs` — efface tous les journaux proxy

Les statistiques globales peuvent être interrogées directement à partir de la table `proxy_logs` via SQL si nécessaire. Le tableau de bord UI peut proposer des vues agrégées.

### Modèles courants

**Détecter un proxy qui bat** (alterne entre success/failure):

```sql
SELECT proxy_url,
       COUNT(*) AS total,
       SUM(CASE WHEN status >= 500 THEN 1 ELSE 0 END) AS errors,
       ROUND(100.0 * SUM(CASE WHEN status >= 500 THEN 1 ELSE 0 END) / COUNT(*), 1) AS error_pct
FROM proxy_logs
WHERE timestamp > datetime('now', '-1 hour')
GROUP BY proxy_url
HAVING error_pct > 5
ORDER BY error_pct DESC;
```

**Trouver des proxys lents** (latence p95 > 2s) :

```sql
WITH ranked AS (
  SELECT proxy_url, latency_ms,
         PERCENT_RANK() OVER (PARTITION BY proxy_url ORDER BY latency_ms) AS pct
  FROM proxy_logs
  WHERE timestamp > datetime('now', '-24 hour')
)
SELECT proxy_url, latency_ms
FROM ranked
WHERE pct >= 0.95
ORDER BY latency_ms DESC;
```

## Arbre de décision de stratégie de rotation

Lorsque plusieurs proxys sont affectés à une étendue, OmniRoute utilise un** stratégie de rotation** pour choisir lequel utiliser pour chaque demande. La stratégie est configurée au niveau de la portée (globale, par fournisseur, par compte, par combo).

### Stratégies disponibles

| Stratégie              | Quand utiliser                              | Compromis                                                             |
| ---------------------- | ------------------------------------------- | --------------------------------------------------------------------- |
| `quality` (par défaut) | Production avec des proxys de qualité mixte | Favorise les proxys bien notés ; peut affamer ceux qui sont mal notés |
| `random`               | Répartition de la charge, confidentialité   | Même distribution ; ignore les signaux de qualité                     |
| `sequential`           | Débogage, tests déterministes               | Parcourt les proxys dans l’ordre ; facile de raisonner                |

### Arbre de décision

```
                    Do you have quality scores for your proxies?
                    │
        ┌───────────┴───────────┐
        │                       │
       YES                     NO
        │                       │
   Are all proxies             │
   roughly equal                  │
   in quality?                   │
        │                       │
   ┌────┴────┐                  │
   │         │                  │
  YES       NO                Use
   │         │              `random`
   │         │              (even spread
   │         │              builds quality
   │         │              data over time)
   │         │
   │    Use `quality`
   │    (best for
   │    mixed quality)
   │
Use `random`
(spread load
evenly)
```

## Exclusion automatique des échecs pour vos propres proxys

Le pool de place de marché 1proxy dégrade déjà automatiquement les proxys défaillants (voir [Proxy Quality Scores](#proxy-quality-scores) ). Pour les procurations** toi** ajouté au registre, le planificateur d'intégrité en arrière-plan (`src/lib/proxyHealth/scheduler.ts`) fournit le même comportement « exclure automatiquement un membre mort de la chaîne », sans rien supprimer :

```bash
# .env — soft-disable a proxy after 3 consecutive failed probes, re-enable it
# automatically once it starts answering probes again.
PROXY_AUTO_DISABLE=true
PROXY_AUTO_REMOVE_AFTER=3
```

Comment il s'intègre dans une chaîne multi-proxy :

1. Le planificateur sonde chaque proxy enregistré chaque `PROXY_HEALTH_INTERVAL_MS` (par défaut 10 min ; minimum 1 min).
2. Après `PROXY_AUTO_REMOVE_AFTER` consécutif** concluant** échecs (un véritable échec de connexion — un délai d'attente ou le propre 5xx de la cible de la sonde ne compte jamais, voir [Proxy Health Checking](#proxy-health-checking-v3816) ), le `status` du proxy est défini sur `dead`.
3. `dead` est l'un des statuts exclus par le filtre d'état actif utilisé par la résolution pool/rotation, donc la rotation d'une portée (round-robin / aléatoire / collant / latence — voir [Rotation Strategy Decision Tree](#rotation-strategy-decision-tree) ) arrête immédiatement de transmettre ce proxy aux nouvelles demandes. Aucun autre proxy du pool n'est affecté, et l'ensemble du pool ne revient jamais silencieusement à une connexion directe — voir la garde fermée en cas de panne [du système proxy à 4 niveaux](#4-level-proxy-system).
4. Le planificateur continue de sonder les proxys `dead` sur le même intervalle. La prochaine sonde réussie ramène `status` à `active` et entre à nouveau dans la rotation — aucun nouvel ajout manuel n'est requis.

C'est délibérément** opt-in et non destructif** : par défaut, le planificateur ne compte et n'enregistre que les échecs (voir la politique C dans `decision.ts`), et `PROXY_AUTO_DISABLE` ne supprime jamais une ligne — c'est à cela que sert l'indicateur `PROXY_AUTO_REMOVE` séparé et plus agressif. Si les deux sont définis sur `true`, `PROXY_AUTO_REMOVE` gagne (un proxy sur le point d'être supprimé n'a aucune utilité pour une désactivation logicielle entre les deux). Consultez la référence [Environment Config](../reference/ENVIRONMENT.md) pour la liste complète des variables.
