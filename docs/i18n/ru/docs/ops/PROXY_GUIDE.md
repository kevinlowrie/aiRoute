## Зачем использовать прокси?

Многие провайдеры AI ограничивают доступ по географическому региону. Разработчики в** Россия, Китай, Иран, Куба, Турция** и другие страны сталкиваются с такими ошибками, как:

```
unsupported_country_region_territory
```

Даже за пределами заблокированных регионов прокси полезны для:

| Вариант использования    | Описание                                                                      |
| ------------------------ | ----------------------------------------------------------------------------- |
| **Географический обход** | Доступ OpenAI, Anthropic, Codex, Copilot из заблокированных стран             |
| **ротация IP**           | Распределяйте запросы по нескольким IPs, чтобы избежать ограничения скорости. |
| **Конфиденциальность**   | Скройте свою настоящую IP от вышестоящих поставщиков                          |
| **Согласие**             | Маршрутизация трафика через определенные юрисдикции                           |
| **Тестирование**         | Имитировать запросы из разных регионов                                        |

## Состояние прокси по умолчанию для новых учетных записей

В** Настройки → Proxy → Глобальная конфигурация** , использовать** Включить прокси по умолчанию для новых подключений** чтобы выбрать исходное состояние прокси для вновь добавленных учетных записей провайдеров.

Новый параметр контролирует начальное состояние прокси-сервера вновь добавленных учетных записей провайдеров. Он не изменяет существующие учетные записи и не заменяет глобальный переключатель прокси. Его начальное значение сохраняет предыдущее поведение. Выключите его один раз, чтобы в будущем создавать учетные записи с отключенным прокси-сервером по умолчанию.

Предпочтение сохраняется как `defaultNewConnectionProxyEnabled` через существующие настройки API. По умолчанию используется `true` если он никогда не сохраняется. Сохранение `false` вступит в силу для последующих новых учетных записей без перезагрузки. `POST /api/providers` принимает необязательное строгое логическое значение `proxyEnabled`; явный `true` или `false` имеет приоритет над значением по умолчанию для создания. Отсутствие дубликата учетной записи или повторное подключение OAuth сохраняют сохраненное состояние этой учетной записи. Отдельные учетные записи по-прежнему можно будет включить или отключить впоследствии.

Выборочная передача поставщика использует настройки по умолчанию для новых учетных записей и сохраняет политику назначения при замене существующих учетных записей. Переключатели прокси не являются переносимыми полями передачи. Полное восстановление резервной копии и историческая миграция JSON/SQL сохраняют существующую семантику восстановления, включая сохраненные значения учетной записи и устаревшие настройки схемы по умолчанию; полное восстановление настроек также может восстановить эту настройку.

Это предпочтение не назначает прокси-сервер и не устанавливает, что он исправен или используется. Фактическая маршрутизация по-прежнему зависит от глобального переключателя прокси-сервера и соответствующей конфигурации прокси-сервера. Синтетические провайдеры без постоянной учетной записи, трафик OAuth до создания учетной записи, прокси-серверы environment/system и сети внешних серверных частей выходят за рамки его компетенции.

## 4-уровневая прокси-система

OmniRoute поддерживает настройку прокси-сервера на** четыре независимых прицела** , решается в приоритетном порядке:

```
Priority Resolution Order (highest → lowest):

  1. 🔵 Account/Connection Proxy  →  per API key / OAuth connection
  2. 🟡 Provider Proxy            →  per provider (e.g., all OpenAI traffic)
  3. 🟠 Combo Proxy               →  per combo/routing configuration
  4. 🟢 Global Proxy              →  all traffic, all providers
```

### Как работает разрешение

Когда OmniRoute отправляет запрос вышестоящему провайдеру, он вызывает `resolveProxyForConnectionFromRegistry()`, который проверяет каждый уровень по порядку:

1. **На уровне аккаунта** — Есть ли прокси-сервер, назначенный для этого конкретного соединения ID?
2. **Уровень провайдера** — Есть ли у этого провайдера назначенный прокси-сервер (например, `openai`)?
3. **Глобальный уровень** — Настроен ли глобальный прокси?
4. **Нет прокси** — Прямое подключение к провайдеру.

Первый матч выигрывает. Это означает, что вы можете установить глобальный прокси-сервер в качестве резервного, но переопределить его для определенных провайдеров или соединений.

### Что проксируется

| Тип трафика           | Прокси? | Примечания                                      |
| --------------------- | ------- | ----------------------------------------------- |
| Завершения чата       | ✅      | Все запросы `/v1/chat/completions`              |
| Вложения              | ✅      | `/v1/embeddings`                                |
| Генерация изображений | ✅      | `/v1/images/generations`                        |
| Аудио (TTS/STT)       | ✅      | `/v1/audio/*`                                   |
| обмен токенов OAuth   | ✅      | Решает `unsupported_country_region_territory`   |
| Тесты подключения     | ✅      | Кнопка «Проверить соединение» использует прокси |
| Обновление токена     | ✅      | Фоновое обновление OAuth                        |
| Синхронизация моделей | ✅      | Список моделей и открытие                       |

## Реестр прокси (CRUD)

Реестр прокси — это таблица SQLite (`proxy_registry`), в которой хранятся все ваши прокси. Каждый прокси имеет:

| Поле       | Тип         | Описание                                                         |
| ---------- | ----------- | ---------------------------------------------------------------- |
| `id`       | UUID        | Уникальный идентификатор                                         |
| `name`     | Нить        | Читабельная этикетка                                             |
| `type`     | Нить        | Протокол: `http`, `https`, `socks5`                              |
| `host`     | Нить        | Имя хоста прокси или IP                                          |
| `port`     | Целое число | Номер порта                                                      |
| `username` | Нить        | Имя пользователя для аутентификации (зашифрованное при хранении) |
| `password` | Нить        | Пароль аутентификации (зашифрованный при хранении)               |
| `region`   | Нить        | Метка географического региона                                    |
| `notes`    | Нить        | Заметки с произвольным текстом                                   |
| `status`   | Нить        | `active` или `inactive`                                          |
| `source`   | Нить        | `manual` или `oneproxy`                                          |

### Создание прокси

**Через панель управления:**

1. Перейти к** Настройки прокси →**
2. Нажмите** Добавить прокси**
3. Заполните тип, хост, порт и дополнительные учетные данные аутентификации.
4. Сохранять

**Через API:**

```bash
curl -X POST http://localhost:20128/api/v1/management/proxies \
  -H "Content-Type: application/json" \
  -d '{
    "name": "US Proxy",
    "type": "http",
    "host": "proxy.example.com",
    "port": 8080,
    "username": "user",
    "password": "pass",
    "region": "US"
  }'
```

### Обновление прокси

```bash
curl -X PATCH http://localhost:20128/api/v1/management/proxies \
  -H "Content-Type: application/json" \
  -d '{
    "id": "proxy-uuid-here",
    "host": "new-proxy.example.com",
    "port": 9090
  }'
```

> **Примечание:** Учетные данные сохраняются, если вы явно не отправите непустые замены. Отправка пустых строк для `username`/`password` сохранит сохраненные значения.

### Удаление прокси

```bash
# Fails if proxy is assigned to any scope
curl -X DELETE "http://localhost:20128/api/v1/management/proxies?id=proxy-uuid"

# Force delete (removes assignments too)
curl -X DELETE "http://localhost:20128/api/v1/management/proxies?id=proxy-uuid&force=1"
```

### Листинг прокси

```bash
curl "http://localhost:20128/api/v1/management/proxies?limit=50&offset=0"
```

### Назначение прокси областям

```bash
# Assign to global scope
curl -X PUT http://localhost:20128/api/settings/proxy \
  -H "Content-Type: application/json" \
  -d '{"level": "global", "proxy": {"type":"http","host":"proxy.example.com","port":8080}}'

# Assign to a specific provider
curl -X PUT http://localhost:20128/api/settings/proxy \
  -H "Content-Type: application/json" \
  -d '{"level": "provider", "id": "openai", "proxy": {"type":"socks5","host":"socks.example.com","port":1080}}'

# Assign to a specific connection/key
curl -X PUT http://localhost:20128/api/settings/proxy \
  -H "Content-Type: application/json" \
  -d '{"level": "key", "id": "connection-uuid", "proxy": {"type":"http","host":"key-proxy.com","port":3128}}'
```

### Решение проблемы эффективного прокси

Проверьте, какой прокси будет использоваться для данного соединения:

```bash
curl "http://localhost:20128/api/settings/proxy?resolve=connection-uuid"
```

Возвращает разрешенный прокси-сервер с его уровнем (`account`, `provider` или `global`) и источником.

### Массовое назначение

Назначьте один прокси нескольким провайдерам или соединениям одновременно:

```bash
curl -X POST http://localhost:20128/api/v1/management/proxies/bulk-assign \
  -H "Content-Type: application/json" \
  -d '{
    "scope": "provider",
    "scopeIds": ["openai", "anthropic", "codex"],
    "proxyId": "proxy-uuid"
  }'
```

### Import/Export

Прокси включены в**Backup/Restore** система. Когда вы экспортируете конфигурацию OmniRoute :

1. Перейти к** Панель мониторинга Настройки → Резервное копирование →**
2. Нажмите** Экспорт** Реестр прокси-сервера — и назначения включены
3. Для восстановления нажмите** Импорт** и загрузите файл резервной копии

Реестр прокси также поддерживает** обновление через порт + хоста** — если вы импортируете уже существующий прокси (тот же хост и порт), он обновляется, а не создает дубликат.

### Устаревшая миграция

Если вы настроили прокси в более старой версии (предварительная регистрация), OmniRoute автоматически перенесет их:

```
Legacy key_value store → proxy_registry + proxy_assignments
```

Это происходит один раз при первом запуске после обновления. Используйте `migrateLegacyProxyConfigToRegistry({ force: true })` для повторного запуска.

## 1proxy Торговая площадка бесплатных прокси

> 🆕** Предоставил [@oyi77](https://github.com/oyi77)** — PR [#1847](https://github.com/diegosouzapw/OmniRoute/pull/1847) (Проблема [#1788](https://github.com/diegosouzapw/OmniRoute/issues/1788) )

OmniRoute интегрируется с** [1 прокси](https://1proxy-api.aitradepulse.com)** платформа сообщества для предоставления доступа к** сотни бесплатных проверенных прокси** со всего мира. Это идеально подходит для пользователей, у которых нет собственной прокси-инфраструктуры.

### Как это работает

```
┌─────────────┐     Sync      ┌─────────────────┐    Rotate     ┌──────────┐
│  1proxy API │ ────────────▶ │  proxy_registry  │ ────────────▶ │ Provider │
│  (external) │   up to 500   │  source=oneproxy │  by quality   │   API    │
└─────────────┘    proxies    └─────────────────┘               └──────────┘
```

1. **Синхронизировать** — OmniRoute извлекает проверенные прокси из 1proxy API
2. **Магазин** Прокси — сохраняются в той же таблице `proxy_registry`, что и `source = 'oneproxy'`
3. **Фильтр** — Фильтровать по протоколу, стране и показателю качества
4. **Поворот** — Выберите лучший прокси, используя качественные, случайные или последовательные стратегии.
5. **Автоматическое ухудшение качества** — Неисправные прокси снижают показатель качества; ниже порогового значения → отмечен как неактивный

### Синхронизация прокси

**Через панель управления:**

1. Перейти к** Настройки → 1proxy** вкладка
2. Нажмите** «Синхронизировать сейчас»**
3. Просмотр статистики: общее количество прокси, количество активных, среднее качество, разбивка по странам.

### Показатели качества прокси

Каждый прокси-сервер 1proxy поставляется с метаданными:

| Поле            | Описание                                          |
| --------------- | ------------------------------------------------- |
| `qualityScore`  | Рейтинг 0-100 по результатам проверки 1 прокси    |

| `anonymity`     | `transparent`, `anonymous` или `elite`            |

Показатели качества динамически корректируются:

- **Неудачные запросы** уменьшить оценку на 10 баллов
- **Оценка падает до ≤ 10** прокси → отмечен как `inactive`
- Неактивные прокси исключены из ротации

```bash

  -d '{"strategy": "random"}'

  -d '{"strategy": "sequential"}'
```

Синхронизация 1proxy имеет встроенный автоматический выключатель:

- После** 5 последовательных сбоев синхронизации** , дальнейшие попытки синхронизации блокируются
- Сбросьте с помощью: `resetOneproxyCircuitBreaker()` или перезагрузите сервер.
- Статус синхронизации доступен на `GET /api/settings/oneproxy?action=status`

## Антиобнаружение и скрытность

OmniRoute не просто маршрутизирует трафик через прокси-сервер — он придает трафику вид легитимности:

### TLS Подмена отпечатка пальца

Использует `wreq-js` для создания отпечатков пальцев TLS, подобных браузеру, в обход систем обнаружения ботов, которые маркируют рукопожатия TLS не связанные с браузером.

### CLI Сопоставление отпечатков пальцев

**Переключение отпечатков пальцев CLI** (`Settings → Security`) переупорядочивает заголовки HTTP и поля тела JSON, чтобы они соответствовали точной подписи собственных двоичных файлов CLI (Claude Code, Codex и т. д.). Это работает** поверх** прокси:

```
Your IP (blocked) → Proxy IP (US) → Provider API
                    + TLS spoof
                    + CLI fingerprint
```

Вы получаете оба** маскировка IP** и** запросить подлинность** одновременно.

### Сохранение прокси-сервера IP

Цветные значки на панели управления показывают, какой уровень прокси активен:

| Значок | Уровень    | Значение                                          |
| ------ | ---------- | ------------------------------------------------- |
| 🟢     | Глобальный | Весь трафик проходит через этот прокси            |
| 🟡     | Поставщик  | Проксируется только трафик этого провайдера       |
| 🔵     | Связь      | Эта конкретная key/account использует этот прокси |

На значке также указан разрешенный прокси-сервер IP для проверки.

## Поиск неисправностей

### "Прокси-сервер SOCKS5 отключен"

Установите `ENABLE_SOCKS5_PROXY=true` в файл `.env` и перезапустите.

### Ошибки «зависания сокета» через прокси

Это нормально для дешевых прокси, которые прерывают простаивающие соединения. OmniRoute уже справляется с этим:

- Отключение поддержки активности при прокси-соединениях (`keepAliveTimeout: 1`)
- Отключение конвейерной обработки (`pipelining: 0`)
- Кэширование диспетчеров во избежание повторных рукопожатий

Если проблема не исчезнет, попробуйте другой прокси или воспользуйтесь функцией ротации 1 прокси.

### «unsupported_country_region_territory» во время OAuth

Убедитесь, что прокси настроен** до** запуск потока OAuth. OmniRoute маршрутизирует обмен токенами OAuth через настроенный прокси-сервер. Сначала установите глобальный прокси или прокси-сервер на уровне поставщика, а затем подключитесь.

### Прокси не используется

Проверьте порядок разрешения:

1. Подтвердите с помощью `GET /api/settings/proxy?resolve=your-connection-id`
2. Проверьте, является ли прокси-сервер `status` `active` (а не `inactive`)
3. Убедитесь, что область назначения прокси соответствует вашему соединению.

### Ошибка синхронизации 1 прокси

Проверьте статус синхронизации:

```bash
curl "http://localhost:20128/api/settings/oneproxy?action=status"
```

Если `consecutiveFailures >= 5`, сработал автоматический выключатель. Перезапустите сервер для сброса или дождитесь ручного сброса.

## Проверка работоспособности прокси (v3.8.16 +)

OmniRoute's** прокси-сервер** механизм (`src/lib/proxyHealth.ts`) обнаруживает неработающие прокси в < 2s посредством быстрой проверки соединения TCP, а затем** кэширует результат** чтобы избежать накладных расходов на каждый запрос.

### Как это работает

```
Request ──▶ ProxyHealthCache.get(url)
             │
             ├─ Cache hit + fresh?  ──▶ return cached status
             │
             └─ Cache miss / stale?  ──▶ TCP connect to host:port
                                          (timeout: FAST_FAIL_TIMEOUT_MS)
                                          ──▶ cache for HEALTH_CACHE_TTL_MS
                                          ──▶ return result
```

Без этого мертвый прокси-сервер будет блокировать каждый запрос на полный `PROXY_TIMEOUT_MS` (по умолчанию 30 секунд) перед сбоем.

### Настраиваемые переменные среды

| Переменная                   | По умолчанию | Цель                                                   |
| ---------------------------- | ------------ | ------------------------------------------------------ |
| `PROXY_FAST_FAIL_TIMEOUT_MS` | `2000`       | Тайм-аут соединения TCP для проверки работоспособности |
| `PROXY_HEALTH_CACHE_TTL_MS`  | `30000`      | Как долго кэшируется результат работоспособности       |

**Рекомендуемые значения:**

| Сценарий                        | Тайм-аут быстрого сбоя | Кэш TTL  | Рассуждение                                                                                     |
| ------------------------------- | ---------------------- | -------- | ----------------------------------------------------------------------------------------------- |
| Высокопроизводительный шлюз API | 1500 мс                | 60000 мс | Агрессивный отказоустойчивый, более длинный кеш для сокращения проверок                         |
| Геораспределенные узлы          | 3000 мс                | 15000 мс | Медленным сетям требуется больше времени; более короткий кеш для быстрого переключения при сбое |
| Разработка/тестирование         | 1000 мс                | 10000 мс | Быстрая итерация на локальных прокси                                                            |
| Скрытность/антиобнаружение      | 2500 мс                | 45000 мс | Избегайте быстрого зондирования, которое может привести к ограничению скорости.                 |

### Проверка работоспособности прокси

```ts
import { getAllProxyHealthStatuses, invalidateProxyHealth } from "omniroute/proxyHealth";

const statuses = getAllProxyHealthStatuses();
for (const s of statuses) {
  console.log(`${s.proxyUrl} → healthy=${s.healthy}, stale=${s.stale}`);
}

// Force re-check a specific proxy
invalidateProxyHealth("http://user:pass@203.0.113.7:8080");
```

Флаг `stale` равен `true`, когда запись в кэше превысила значение `HEALTH_CACHE_TTL_MS` и следующий запрос вызовет новую проверку.

### Значения по умолчанию для каждого типа прокси

При проверке работоспособности используются разумные значения по умолчанию, основанные на схеме URL :

| Схема                      | Порт по умолчанию |
| -------------------------- | ----------------- |
| `http://`                  | 8080              |
| `https://`                 | 443               |
| `socks5://` / `socks5h://` | 1080              |

Пользовательские порты в URL (`http://host:9999`) всегда имеют приоритет над портами схемы по умолчанию.

## Прокси-аналитика и наблюдаемость

OmniRoute отслеживает использование каждого прокси-сервера, помогая операторам диагностировать шаблоны маршрутизации, скачки задержек и повторяющиеся сбои.

### Что отслеживается

Для каждого запроса через настроенный прокси-сервер OmniRoute записывает:

| Метрика      | Описание                                                       |
| ------------ | -------------------------------------------------------------- |
| `proxy_url`  | Полный прокси-сервер URL (с замаскированными учетными данными) |
| `provider`   | Поставщик апстрима ID (openai, anthropic и т. д.)              |
| `latency_ms` | Общее время прохождения, включая рукопожатие прокси-сервера    |
| `connect_ms` | TCP только время подключения                                   |
| `status`     | код состояния HTTP от восходящего потока                       |
| `error`      | Класс ошибки, если запрос не выполнен                          |
| `timestamp`  | ISO 8601 UTC                                                   |

### Доступ к данным

```bash
# Recent proxy events
curl -H "Authorization: Bearer $OMNIROUTE_KEY" \
  "http://localhost:20128/api/usage/proxy-logs?limit=100"
```

Настоящая конечная точка — `/api/usage/proxy-logs` (см. `src/app/api/usage/proxy-logs/route.ts`). Эта конечная точка поддерживает:

- `GET /api/usage/proxy-logs` — получение журналов прокси-сервера
- `DELETE /api/usage/proxy-logs` — очистить все журналы прокси

При необходимости совокупную статистику можно запросить непосредственно из таблицы `proxy_logs` через SQL. Панель мониторинга UI может предлагать агрегированные представления.

### Общие шаблоны

**Обнаружение нестабильного прокси** (чередуется между success/failure):

```sql
SELECT proxy_url,
       COUNT(*) AS total,
       SUM(CASE WHEN status >= 500 THEN 1 ELSE 0 END) AS errors,
       ROUND(100.0 * SUM(CASE WHEN status >= 500 THEN 1 ELSE 0 END) / COUNT(*), 1) AS error_pct
FROM proxy_logs
WHERE timestamp > datetime('now', '-1 hour')
GROUP BY proxy_url
HAVING error_pct > 5
ORDER BY error_pct DESC;
```

**Найдите медленные прокси** (задержка p95 > 2 с):

```sql
WITH ranked AS (
  SELECT proxy_url, latency_ms,
         PERCENT_RANK() OVER (PARTITION BY proxy_url ORDER BY latency_ms) AS pct
  FROM proxy_logs
  WHERE timestamp > datetime('now', '-24 hour')
)
SELECT proxy_url, latency_ms
FROM ranked
WHERE pct >= 0.95
ORDER BY latency_ms DESC;
```

## Дерево решений стратегии ротации

Когда одной области назначено несколько прокси, OmniRoute использует** стратегия ротации** чтобы выбрать, какой из них использовать для каждого запроса. Стратегия настраивается на уровне области действия (глобальная, для каждого поставщика, для каждой учетной записи, для каждой комбинации).

### Доступные стратегии

| Стратегия                | Когда использовать                         | Компромисс                                                                                        |
| ------------------------ | ------------------------------------------ | ------------------------------------------------------------------------------------------------- |
| `quality` (по умолчанию) | Производство с прокси смешанного качества  | Отдает предпочтение прокси с высоким рейтингом; могут уморить голодом тех, кто с низким рейтингом |
| `random`                 | Распределение нагрузки, конфиденциальность | Равномерное распределение; игнорирует сигналы качества                                            |
| `sequential`             | Отладка, детерминированное тестирование    | Циклически переключает прокси по порядку; легко рассуждать                                        |

### Дерево решений

```
                    Do you have quality scores for your proxies?
                    │
        ┌───────────┴───────────┐
        │                       │
       YES                     NO
        │                       │
   Are all proxies             │
   roughly equal                  │
   in quality?                   │
        │                       │
   ┌────┴────┐                  │
   │         │                  │
  YES       NO                Use
   │         │              `random`
   │         │              (even spread
   │         │              builds quality
   │         │              data over time)
   │         │
   │    Use `quality`
   │    (best for
   │    mixed quality)
   │
Use `random`
(spread load
evenly)
```

## Автоматическое исключение сбоев для ваших собственных прокси

Пул торговой площадки 1proxy уже самостоятельно автоматически ухудшает качество неисправных прокси (см. [Показатели качества прокси](#proxy-quality-scores) ). Для прокси** ты** добавленный в реестр, фоновый планировщик работоспособности (`src/lib/proxyHealth/scheduler.ts`) обеспечивает такое же поведение «автоматически исключать мертвого участника из цепочки», ничего не удаляя:

```bash
# .env — soft-disable a proxy after 3 consecutive failed probes, re-enable it
# automatically once it starts answering probes again.
PROXY_AUTO_DISABLE=true
PROXY_AUTO_REMOVE_AFTER=3
```

Как это вписывается в цепочку с несколькими прокси:

1. Планировщик проверяет каждый зарегистрированный прокси-сервер каждый `PROXY_HEALTH_INTERVAL_MS` (по умолчанию 10 минут; минимум 1 минута).
2. После `PROXY_AUTO_REMOVE_AFTER` подряд** убедительный** сбои (реальный сбой соединения — по тайм-ауту или собственный 5xx цели зонда никогда не учитываются, см. [Проверка работоспособности прокси-сервера](#proxy-health-checking-v3816) ), `status` прокси-сервера устанавливается на `dead`.
3. `dead` — это один из статусов, который фильтр состояния активности, используемый разрешением pool/rotation, исключает, поэтому ротация области (циклический/случайный/липкий/задержка — см. [Дерево решений стратегии ротации](#rotation-strategy-decision-tree) ) немедленно прекращает передачу этого прокси новым запросам. Никакие другие прокси-серверы в пуле не затрагиваются, и весь пул никогда автоматически не возвращается к прямому соединению. — см. [4-уровневую защиту от закрытия прокси-системы](#4-level-proxy-system).
4. Планировщик продолжает проверять прокси-серверы `dead` с тем же интервалом. При следующем успешном зондировании `status` возвращается в `active`, и он снова входит в вращение — повторного добавления вручную не требуется.

Это намеренно** согласие и неразрушающий** : по умолчанию планировщик только подсчитывает и регистрирует сбои (см. политику C в `decision.ts`), а `PROXY_AUTO_DISABLE` никогда не удаляет строку —, для чего предназначен отдельный, более агрессивный флаг `PROXY_AUTO_REMOVE`. Если для обоих установлено значение `true`, `PROXY_AUTO_REMOVE` выигрывает (прокси-сервер, который будет удален, не нуждается в программном отключении между ними). Полный список переменных см. в справочнике [по конфигурации среды](../reference/ENVIRONMENT.md).
